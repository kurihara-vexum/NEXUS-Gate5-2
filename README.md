# Gate5 提出物

端末貸出管理の異常系を洗い出し、データ破損や不整合に直結する高優先度5項目だけを実装したミニアプリです。

## 1. 起動手順

### 動作環境

- Node.js 22.5以上（標準の `node:sqlite` を使用）
- npm（外部パッケージなし）

### 環境構築コマンドと起動コマンド

```bash
git clone https://github.com/kurihara-vexum/NEXUS-Gate5-2.git
cd NEXUS-Gate5-2
npm install
npm start
```

ブラウザで <http://localhost:3000> を開きます。自動テストは `npm test` で実行できます。

初期データには、貸出可能な `PC-001`、貸出中の `PC-002`、整備中の `TB-001` などが入っています。画面上部の「確認データをリセット」で何度でも初期状態に戻せます。

### 必須エラー状態の確認

- 既に貸出中の端末：画面の「貸出中端末のエラーを表示」を押すと、`PC-002` が選択され「この端末は既に貸出中です。別の端末を選択してください。」が赤く表示されます。
- 過去の返却予定日：画面の「過去日のエラーを表示」を押すと、貸出可能端末と `2020-01-01` が入力され「返却予定日は今日以降の日付を指定してください。」が赤く表示されます。

どちらもエラー時に貸出記録や端末状態は更新されません。

## 2. 洗い出しの結果

- 洗い出した項目数: 16 件
- カバーした観点:12345678のうち 8 カテゴリ
- 補完後のフロー図で増えたひし形の数: 5 個

観点カテゴリは、1.正常系、2.入力値、3.境界値、4.状態遷移、5.利用者・権限、6.データ整合性、7.同時実行、8.障害・復旧です。詳細と補完フローは [`docs/gate5-flow.md`](docs/gate5-flow.md) に記載しました。

## 3. 実装した項目 / 実装しなかった項目

| No | 項目 | 優先度 | 実装 | 理由 |
| -- | -- | --- | -- | -- |
| 1 | 正常な貸出登録 | 中 | × | 今回は異常系・整合性保護を優先 |
| 2 | 正常な返却登録 | 高 | ○ | 貸出記録と端末状態の不整合を防ぐ基盤 |
| 3 | 返却予定日が未入力 | 中 | × | HTML必須入力のみ。サーバー側は不正日付として拒否 |
| 4 | 返却予定日が過去日 | 高 | ○ | 誤った期限データが残るため |
| 5 | 存在しない日付（2月30日など） | 中 | × | サーバー検証は実装済みだが高優先5件には数えない |
| 6 | 返却予定日が今日 | 低 | × | 境界値テストのみで十分と判断 |
| 7 | 既に貸出中の端末を再貸出 | 高 | ○ | 二重貸出を防ぐ最重要項目 |
| 8 | 整備中端末の貸出 | 高 | ○ | 使用不能端末の貸出記録を防ぐため |
| 9 | 存在しない端末ID | 中 | × | 通常UIから発生せず、APIでは拒否 |
| 10 | 無効な利用者への貸出 | 高 | ○ | 退職者等への資産紐付けを防ぐため |
| 11 | 存在しない利用者ID | 中 | × | 通常UIから発生せず、APIでは拒否 |
| 12 | 同じ画面を2人が同時更新 | 高 | — | No.7の防御策に包含（更新日時による競合検知） |
| 13 | 貸出記録作成後に端末更新が失敗 | 高 | — | No.7の防御策に包含（同一トランザクション） |
| 14 | 返却記録更新後に端末更新が失敗 | 高 | — | No.2の防御策に包含（失敗時ロールバック） |
| 15 | 有効貸出のない端末を返却 | 中 | × | APIでは拒否するが画面に操作を出さない |
| 16 | DB接続断・ディスク障害 | 中 | × | エラー応答とロールバックまで。運用監視は対象外 |

実装数は機能単位で5件（No.2、4、7、8、10）です。No.12〜14は独立機能として数を増やさず、それぞれ二重貸出防止・返却整合性の防御策として含めました。

## 5. 振り返り

### 5-1. 自分の洗い出しで、項目が 0 件だった観点カテゴリはどれですか。

ありません。8カテゴリすべてで最低1件を洗い出しました。ただし「障害・復旧」はDB障害時のロールバックとエラー応答に留まり、監視・再実行・バックアップ復旧までは今回のスコープ外です。

### 5-2. 「言われれば当たり前」だったのに気づけなかった項目を 3 つ挙げ、なぜ自力で気づけなかったかを書いてください。

1. アプリの事前チェックだけでは同時クリックによる二重貸出を防げないこと。画面を一人で順番に操作する想定に偏り、同時実行を時間軸で考えられていませんでした。
2. 貸出記録と端末状態の片方だけ成功すると、一覧表示と実績が食い違うこと。処理を画面単位で見ており、複数テーブルを一つの業務処理として捉えられていませんでした。
3. 「日付形式が正しい」と「実在する日付である」は別であること。必須・形式チェックで十分だと思い、2月30日のような暦上の不正値を見落としていました。

### 5-3. Gate1 の振り返りで書いた「確認しに行くこと」リストと比べて、増えた観点は何ですか。

Gate1では状態遷移、権限、表示、メッセージ、履歴、同時更新を主に確認していました。Gate5ではさらに、DB制約を最後の防波堤にすること、複数テーブル更新を一つのトランザクションにまとめること、途中失敗時のロールバックを意図的に発生させて検証すること、日付の暦妥当性を確認することが増えました。
