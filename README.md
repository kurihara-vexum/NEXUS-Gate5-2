# Gate5 提出物

PC貸出処理について、洗い出し表の高優先度項目（データ破損・不整合・不正操作）と、提出写真で必須の過去日エラーを実装したミニアプリです。

## 1. 起動手順

### 動作環境

- Node.js 22.5以上（標準の `node:sqlite` を使用）
- 外部パッケージなし

### 環境構築コマンドと起動コマンド

```bash
git clone https://github.com/kurihara-vexum/NEXUS-Gate5-2.git
cd NEXUS-Gate5-2
npm start
```

ブラウザで <http://localhost:3000> を開きます。テストは `npm test` で実行できます。画面上部の「初期状態に戻す」で確認用データを初期化できます。

### 必須写真の状態を作る手順

1. 正常時：`PC-001`、明日以降の日付、利用目的を入力して「貸出を登録」を押す。
2. 状態チェック：初期状態へ戻し、貸出中の `PC-002` を選んで登録する。
3. 入力値チェック：初期状態へ戻し、`PC-001` と `2020-01-01`、利用目的を入力して登録する。
4. 任意の例外（休職・退職者）：いったん停止し、`CURRENT_USER_ID=3 npm start` で再起動して `PC-001` の貸出を試す。

エラー時は貸出記録も端末状態も更新されません。`CURRENT_USER_ID` は確認環境でログイン済み社員を表すサーバー設定で、ブラウザから借用者IDを指定・変更することはできません。

- 洗い出した項目数: 20 件

## 3. 実装した項目 / 実装しなかった項目

| No | 項目 | 優先度 | 実装 | 理由 |
| -- | -- | --- | -- | -- |
| 1 | 既に貸出中の端末を選択 | 高 | ○ | トランザクション内で端末状態と未返却貸出を再確認し、部分UNIQUEインデックスでも二重貸出を防止 |
| 2 | 休職・退職した社員が貸出申請 | 高 | ○ | 認証済み社員が無効なら登録前に拒否 |
| 3 | 貸出可能端末が0件 | 低 | × | データ不整合に直結しないため今回の対象外 |
| 4 | 貸出台数の上限超過 | 中 | × | 上限台数が正常系仕様で未確定のため |
| 5 | 同じ申請を2回送信 | 中 | × | 申請キーによる冪等化は今回の対象外。端末単位の重複はNo.1のDB制約で防止 |
| 6 | 2人が同時に同じ端末を選択 | 高 | ○ | `BEGIN IMMEDIATE`、更新日時の競合検知、DB制約の三段階で先行1件だけを確定 |
| 7 | ブラウザバックから再送信 | 中 | × | 申請キーと確認画面の永続化が必要なため |
| 8 | 返却予定日が過去 | 中 | ○ | 必須写真の対象。サーバーで明日より前の日付を拒否 |
| 9 | 返却予定日が先すぎる | 中 | × | 最大貸出期間の業務決定が必要なため |
| 10 | 存在しない日付 | 中 | ○ | 日付文字列を厳密に検証する基礎防御として実装 |
| 11 | 返却予定日が当日 | 中 | ○ | 洗い出し表どおり明日以降のみ許可 |
| 12 | 返却予定日が空欄 | 中 | ○ | HTMLとサーバーの両方で拒否 |
| 13 | 利用目的が空欄 | 中 | ○ | 正常系の必須入力を満たすため実装 |
| 14 | 利用目的が100文字超過 | 中 | ○ | DB定義を超える値を保存しないため実装 |
| 15 | 利用目的に特殊文字 | 中 | × | 許可文字の詳細仕様が未確定のため |
| 16 | 借りていない端末を返却 | 中 | ○ | 本人の未返却貸出と端末状態の両方を確認し、不一致なら更新しない |
| 17 | 延滞中ユーザーが新規貸出 | 中 | × | 今回は高優先度と必須写真に絞ったため |
| 18 | 複数テーブル更新の途中で失敗 | 高 | ○ | 貸出・返却とも貸出記録と端末状態を同一トランザクションで更新し、失敗時に全体をロールバック |
| 19 | DB接続断・タイムアウト | 高 | ○ | 未確定の更新はトランザクションでロールバックし、内部エラー時は成功表示を出さない |
| 20 | 他人のIDを指定して実行 | 高 | ○ | 借用者IDを画面・API入力にせず、サーバーの認証済み社員IDだけを使用。返却も所有者を確認 |

意図して選定した中心実装は高優先度6件（No.1、2、6、18、19、20）と、必須写真のNo.8です。No.10〜14、16は正常系を安全に成立させるための基礎検証としてあわせて実装しています。

## 5. 振り返り

### 5-1. 自分の洗い出しで、項目が 0 件だった観点カテゴリはどれですか。

ありません。8カテゴリすべてで最低1件を洗い出しました。

### 5-2. 「言われれば当たり前」だったのに気づけなかった項目を 3 つ挙げ、なぜ自力で気づけなかったかを書いてください。

1. 画面で空きに見えても、確定までの間に別の人が借りる可能性があること。一人で順番に操作する前提で考え、同時実行を時間軸で捉えられていませんでした。
2. 貸出記録と端末状態の片方だけ成功すると、一覧と実績が食い違うこと。処理を画面単位で見ており、複数テーブルを一つの業務処理として捉えられていませんでした。
3. 画面のプルダウンを制限しても、APIへ他人のIDを直接送信できること。通常の画面操作だけを想定し、サーバー側の信頼境界を意識できていませんでした。

### 5-3. Gate1 の振り返りで書いた「確認しに行くこと」リストと比べて、増えた観点は何ですか。

状態遷移・権限・表示・メッセージに加えて、同時実行時の再確認、DB制約を最後の防波堤にすること、複数テーブル更新のトランザクション、途中失敗時のロールバック、ブラウザを信用せず認証済み本人をサーバーで確定する観点が増えました。
